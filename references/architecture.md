# 架构设计与关键决策记录

> 脱敏版：不含账号人设/城市/路径/话术。决策记录保留「为什么这么做」，供复刻者避坑。

## 1. 为什么三层分离

早期版本把语义判断写死在采集脚本（关键词白名单），缺点：

- 关键词表越大越难维护，误杀/漏杀并存
- 每次调规则都要改脚本重启，迭代慢

最终架构：**能脚本化的全脚本化，需要判断的交给 LLM**。

| 层 | 职责 | 技术 | 触发 |
|---|---|---|---|
| 机械层 | 滚动采集、广告/老帖/去重硬过滤、画像投喂、落盘 | 纯 Node（零依赖） | 定时器（如每 10min 检查一次，非活跃时段跳过） |
| 语义层 | 读帖判断相关度与等级、按人设起草、校验链 | LLM Agent | 采集落盘后由 Agent 逐条处理 |
| 执行层 | 打开详情页发布、回显验证、写日志 | 纯 Node | 语义层审核通过后显式调用 |

收益：机械层稳定且不烧 token；语义层迭代不需要动脚本；发布是独立显式动作，天然满足「预览模式绝不发帖」。

## 2. 零依赖 CDP 客户端

不引入 puppeteer/playwright，直接用 Node 内置 `WebSocket` + `fetch` 实现极简 CDP：

```
GET  http://127.0.0.1:<port>/json/version   → 浏览器级 webSocketDebuggerUrl
GET  http://127.0.0.1:<port>/json           → 标签页列表
WS   Target.createTarget / Page.navigate / Runtime.evaluate / Input.dispatchMouseEvent
```

配套实现要点：
- 自建请求-响应配对（msgId → pending Map），20s 超时兜底
- 复用本机**已登录**浏览器调试端口 → 不维护登录态/cookie，登录态失效由人处理
- 沙盒隔离：独立浏览器 user-data-dir + headless，与日常浏览器分开

## 3. 采集链路与硬过滤

```
滚动(1.2-2.2s 随机, 共 N 次) → EXTRACT(页内 JS 抽取卡片)
  → 广告卡剔除(note_id 非 24hex / 赞助角标)
  → 老帖硬过滤(时间线索解析, 见 SKILL.md)
  → seen/replied/skipped 去重
  → 超上限截断 → candidates.json 落盘 + candidates_history.jsonl 追加备份
```

经验点：
- **EXTRACT 用页内注入 JS**（Runtime.evaluate 返回数组），比逐卡 CDP 操作快且省请求
- 卡片 0 条时输出页面诊断（title/note-item 数量/body 前 150 字），区分「选择器失效」与「页面异常」与「账号风控页」
- 候选 URL 持久化到 jsonl（保留 xsec_token），防止下一轮覆盖后丢失详情链接——曾因丢失 token 导致历史候选全部打不开

## 4. 时间过滤的跨年坑

MM-DD 短格式（如 `08-12`）不能想当然判新帖：

- 补成今年日期 → 若晚于今天说明是去年 → 回退一年 → 再按距今天数判
- 否则 1 月初会把去年 12 月的帖子误判成 1 天新帖混入

## 5. URL 规范化

搜索结果卡片 href 形如 `/search_result/<id>?xsec_token=...`。若直接打开：

- 详情页评论框不存在 → 发布失败
- 统一 `https://www.xiaohongshu.com/explore/<id>?<保留原query>`

## 6. 状态机设计

三集合分离的动机：

- `replied` 永久（发过就不碰）；`seen` 只是「最近见过」窗口（裁剪到 3000，只防短周期内重复刷到同帖）；`skipped` 显式放弃
- 若混在一个集合，裁剪会误伤 replied，导致重复评论同一篇

pending 机制：采集落盘后语义层可能不在线（定时器与 Agent 异步）。pending 未清 → 下一轮跳过刷新（保护未处理候选）；超 3h 未处理说明 Agent 崩了 → 归档 skipped 防死锁。

互斥锁：`fs.mkdirSync(lockdir)` 原子性实现，collect 与 feed_train 互斥；stat mtime 超 10min 视为崩溃残留自动接管。

## 7. 画像投喂（养号）设计

目的：让推荐算法学账号兴趣 → 推荐流供给变好（比搜索模式省风控额度）。

- 每轮从候选/搜索结果挑兴趣相关笔记，洗牌随机取 ≤2 篇
- 详情页停留 10-20s、间隔 4-8s（真人节奏）
- 低频点赞 ≤2/轮（点赞目标：主笔记点赞区，需与卡片点赞选择器区分——这是实测探测出来的坑）
- 失败不影响主流程；绝不评论不发布

## 8. 发布验证（防误记）

不能以「点了发送按钮」或「输入框清空」判断成功：

- 点发送后等待 3-4s
- 判据 = 页面 body 文本包含回复前 12 字片段（说明评论真的出现在评论区）
- 输入框清空仅辅助信号
- 成功才写 replied + 日志；失败不落库、不重试（下轮重新走语义层）

## 9. 运行卫生

- **单标签纪律**：全程只保留 1 个站内标签；每次启动自清理残留详情页标签
- 非活跃时段跳过（active_hours 配置）
- 北京时间时间戳函数（本地时间组件拼装），避免 UTC 差 8h 的日志错位
- 每轮日志带可 grep 关键字（`✅/⚠️/❌`），巡检一眼定位

## 10. 风控冷却体系

所有「安全验证 / 请求太频繁」页面标题信号 → 写冷却时间戳 → 后续轮次直接跳过直至到期。冷却是**状态机的一部分**而非脚本内 if——重启/崩溃后依然生效。
